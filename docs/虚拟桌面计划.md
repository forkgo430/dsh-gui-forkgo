# 虚拟桌面计划

> 目标：让 DSH 的 GUI 插件能在一个**独立的 TS 子会话**里操作电脑，不抢用户的鼠标键盘。
>
> 这是一份**活文档**。每次有新发现、新结论、新失败都要追加，不要新建别的文件。
>
> 最后更新：2026-11-21 00:50

---

## 0. 一句话现状

**子会话能创建、能连接，但登录不进去；原因已定位到「父会话用 PIN 登录」。豆包能成功，是因为它手里有一个可用于 NTLM 认证的明文密码。这个密码的来源已查到一个可疑凭据，但技术上无法解开。**

---

## 1. 目标与背景

### 1.1 为什么要做子会话

普通桌面自动化会**抢用户的鼠标键盘**。DSH 的 GUI 插件（`dsh-gui-forkgo`）目前直接操作用户会话，AI 一动鼠标用户就没法干活。

Windows 有一个原生机制可以解决：**Child Session（子会话）**——同一台机器上、同一用户、独立的桌面会话。

### 1.2 参考实现

| 来源 | 说明 |
|---|---|
| [微软 Child Sessions 文档](https://learn.microsoft.com/en-us/windows/win32/termserv/child-sessions) | 官方 API 说明 |
| [Ray-Desktop](https://github.com/raydoomed/Ray-Desktop) | MIT 开源，.NET WinForms + RDP ActiveX，**声称免密** |
| 豆包工作（DoubaoWork） | 商业实现，本机实测**能成功** |

### 1.3 本机环境

```
OS          : Windows 10 家庭中文版 build 19045
账户        : 金东权（本地账户，Administrators 组成员）
子会话状态   : WTSIsChildSessionsEnabled = True

```

## 2. 已确证的关键事实

### 2.1 父会话是 PIN 登录（这是所有失败的根因）

```
HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Authentication\LogonUI
  LastLoggedOnProvider = {D6886603-9D2F-4EB2-B667-1971041FA96B}   ← PIN 凭据提供程序
  LastLoggedOnUser     = .\金东权

HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\PasswordLess\Device
  DevicePasswordLessBuildVersion = 2    ← Hello/无密码优先（0 才是传统密码优先）
```

PIN 由 TPM/Hello 容器**本地验证**，不产生可复用于 loopback RDP 的密码材料。

**微软文档说 `Connect()` 会自动登录，例外只列了两条（智能卡、启用晚于登录）。实际上还有第三条未记录的例外：父会话用 Windows Hello / PIN 登录。**

## 3. 已排除的路径（别再重复尝试）

| 路径 | 结果 | 详情 |
|---|---|---|
| `WTSQueryUserToken` | ❌ | `err=1314 ERROR_PRIVILEGE_NOT_HELD`，需要 `SE_TCB_NAME`；实测 token 里只有 6 个特权，**提权到管理员也拿不到** |
| `LogonUserW` 空密码 | ❌ | `err=1326 ERROR_LOGON_FAILURE` |
| `LogonUserW` 猜密码 | ❌ | 试过 `asdfghjkl`（用户提供，被拒），INTERACTIVE/NETWORK/NETWORK_CLEARTEXT 三种类型全失败 |
| Windows Sandbox | ❌ | 家庭版不支持 |
| Hyper-V | ❌ | 家庭版不支持 |
| `ConnectToShadowSession` 属性 | ❌ | 本机 `IMsRdpExtendedSettings` 只认 `ConnectToChildSession`；`ConnectToShadowSession` 返回 `0x8000FFFF E_UNEXPECTED` |
| 显式传 `UserName`/`Domain` | ❌ | 变体 B 实测：仍停在 `LogonUI.exe`，34.2s 断开 |
| `PromptForCredentials` / `AllowPromptingForCredentials` | ❌ | 返回 `0x8000FFFF`，属性不存在 |

## 5. 当前的核心矛盾

| 事实 | 推论 |
|---|---|
| session 3 是 NTLM 交互式登录 | 必须有可计算凭据材料 |
| `LogonUserW` 是唯一凭据 API | 必须是**明文密码** |
| 凭据存在 Credential Manager | 需要一个能解的加密容器 |
| 凭据 `LastWritten = 2026-08-21` | 早于豆包安装（10-29）两个月 |
| 用户明确说**从未输过密码** | 凭据不是用户输的 |

**三种可能的解释：**

1. **别的产品写入的凭据被豆包复用**（Cicic / WorkBuddy / Coze / 联想相关）
2. **豆包安装时迁移了旧产品的凭据**
3. 系统时间或 FILETIME 解析有误（已复核，解析正确）

### 三、DPAPI 路线彻底排除（239400 次穷举）


### 六、新发现的第二套机制：cua_sandbox

日志里大量出现，与 pip shadow session 是**两套独立体系**：

```

sandbox.bash.taskOutput
sandbox_id: sandbox-37626212-1f44-4941-94fe-eec933aa2038
```

`DoubaoWork\...\sandbox_runtime\bases\` 下有独立的 node.exe / npm 运行时。

**这说明豆包有两条执行通道：**

### 四、帧哈希去重 + 暖 worker

**帧哈希**（`desktop/frame_cache.py`）：

```python
def frame_hash(image, grid=64):
    src = image if image.mode == "RGB" else image.convert("RGB")
    small = src.resize((grid, grid), Image.Resampling.BOX)
    return hashlib.blake2b(small.tobytes(), digest_size=16).hexdigest()
```

性能实测（1080p）：

```
优化前  37.65 ms   ← convert("RGB") 对已是 RGB 的图也做完整拷贝
优化后   3.10 ms   ← 只在模式不对时转
提升    12 倍
```

grid 从 16 到 128 精度都一样（都能分辨差 1 个像素值），64 是稳妥选择。

**暖 worker**：后台线程每 2s 空转一次截图，把 DWM flush / DXGI 输出枚举 /
相机对象保持热态。挂在 `__main__.py` 的 lifespan 里启停，失败不影响主流程。

实测（间隔 0.2s，跑 0.75s）：

```

stats before stop = {running: True, warmups: 4, errors: 0}
stats after stop  = {running: False, warmups: 4, errors: 0}
```

### 三、DPI 变化监视

`frame_cache.DisplayWatcher`：每 1 秒（节流）读一次显示器布局签名，
包含每个显示器的 index / rect / effective_dpi / scale / orientation。
签名变了就让帧哈希缓存整体失效。

**为什么需要：** `GetDisplays()` 本身每次真实调用 `GetDpiForMonitor`，是实时的；
但帧哈希缓存是按 `(区域, 哈希)` 记的。缩放一变，同一块区域的物理像素换了含义，
旧缓存会给出错误的「这一帧没变」判断。

**实测：**

